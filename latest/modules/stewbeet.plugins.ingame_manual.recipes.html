      🧾 recipes#

      Recipe rendering package.

      Re-exports the dispatcher and the public registry surface. Existing call sites keep importing from ..recipes. The built-in type renderers load on first lookup rather than on import, see load_builtin_renderers().

      • 🗂️ types

      The typed wiki button produced by the recipe renderer.

      A single wiki button (icon + hover) with a deferred click target.

      blue_craft marks a craft that has no result (only ingredients), used by overflow handling. target is either a PageRef (resolved after page ordering) or a literal click-event dict (e.g. an author-provided open_url from a WikiButton).

      >>> button = WikiButtonRender(glyph="X", hover=["Some hover text"])
>>> button.priority, button.target is None
(1, True)

      collection#

      Craft collection and pure recipe helpers.

      collect_for_item gathers an item’s own recipes, the crafts that consume it, and mining pseudo-recipes from no-silk-touch drops. remove_unknown_crafts keeps only craft types that have a registered CraftRenderer, so it auto-extends with new types.

      registry#

      Recipe-type renderer base class and the global registry.

      Each recipe type has one CraftRenderer that owns all of its rendering: the main page layout (render_body()), the wiki-button hover lines (append_hover()), its human name (name), its high-res template glyph (static_glyph()) and its low-res image (build_image()). Renderers register themselves into CRAFT_RENDERERS via register_craft_renderer(), so adding a recipe type is one new file + one call.

      The r argument passed to renderer methods is the RecipeRenderer dispatcher, exposing r.config / r.glyphs / r.images / r.item_component(...) / r.append_or_invisible(...) / r.render_main(...).

      class CraftRenderer[source]#

      Bases: object

      Base class for a recipe-type renderer.

      Subclass it, set types (and optionally name), override the render methods you need, then call register_craft_renderer() on an instance.

      >>> class _EchoRenderer(CraftRenderer):
...     types = ("test_echo",)
...     name = "Echo"
>>> _ = register_craft_renderer(_EchoRenderer())
>>> get_craft_renderer("test_echo") is CRAFT_RENDERERS["test_echo"]
True
>>> get_craft_renderer("unknown_type") is None
True
>>> del CRAFT_RENDERERS["test_echo"]

      load_builtin_renderers() → dict[str, CraftRenderer][source]#

      Import the built-in renderer modules once, then return the populated registry.

      Those modules register themselves as a side effect of executing, which under PEP 810 never happens on its own since nothing imports them by name. Every lookup goes through here instead of relying on the package import that used to pull them in eagerly.

      Returns:

      The registry, with every built-in renderer present

      Return type:

      dict[str, CraftRenderer]

      renderer#

      The RecipeRenderer dispatcher.

      Builds craft content, item hover components and wiki buttons for a manual by delegating each recipe type to its registered CraftRenderer. Keeps the shared prologue and button scaffolding; the per-type layout/hover/glyph/image live under types.

      class RecipeRenderer(manual: Manual)[source]#

      Bases: object

      Dispatcher: delegates per-type rendering to the registry, owns the shared scaffolding.

      eq=False keeps identity semantics: this class and Manual reference each other, so field-based equality would recurse.

      button_for_item(
      item_id: str,
      index: int = 0,
      ) → WikiButtonRender | None[source]#

      Build the wiki button of another item’s craft, linking to that item’s page.

      Use it to cross-link related pages, e.g. show the Starlight Infuser’s recipe button on the Stardust Pillar page. index selects which of the item’s crafts to render (same order as its own page). Returns None (with a warning) if the item has no such craft.
